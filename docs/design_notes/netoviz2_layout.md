# netoviz2 のレイアウト

netoviz2 (汎用トポロジビューワー) が、ノードとリンクをどう配置するかの設計と、その方針を決めた経緯の記録です。
実装は `repos/netoviz2/src/render/` (`forceRenderer.ts`、`layout/`) にあります。全体の設計は [netoviz2_requirements.md](../work/plans/netoviz2_requirements.md)、データ形式と API は [netoviz2_data_format.md](../netoviz2_data_format.md) を参照してください。

## 1. 方針 (結論)

* レイアウトエンジンは **force (d3-force)** と **stress (自前のストレス最小化)** の 2 つ。**既定は stress**。
* **ELK (elkjs) は採用しない。** 検証 (3 参照) では品質で自前の stress に及ばず、ライセンス (EPL-2.0) への対応と約 1.5MB のサイズが必要になるため。
* 2 つのエンジンは、画面で切り替えて比較できる (`?layout=<force|stress>`、`&compare=<engine>`)。各パネルが、所要時間・リンクの交差数・ノードの重なりを表示する。
* 階層的な表示 (ELK layered が得意とするもの) は、レイアウトエンジンではなく、段階 4 の dependency 表示 (レイヤ帯) で別に扱う。

## 2. 要求

* ネットワーク構成図として、**リンクの交差とノード・ラベルの重なりをできるだけ少なく**する。構成図向けの専用エンジンが無いため force-simulation を使ってきたが、force 以外で解決できるなら検討する。
* term-point (TP) を明示して、どの TP でノード間がつながっているかを分かるようにする。
* 想定規模: 数百ノード、1 デバイスあたり数十〜100 TP (実データの最大は全レイヤ合計で 315 ノード・720 TP)。表示までの時間は数秒以内。
* 依存は寛容なライセンス (MIT 系) のものにする (本プロジェクトは MIT)。

## 3. 採用した設計

### 3.1 共通の構造

* **レイアウトの対象はノードだけ。** TP は物理シミュレーションの対象にせず、ノードの円周上の**ポート**として配置する。ポートの向きは、つながっている相手ノードの方向 (複数ならその方向の平均。無ければ全体の重心から外向き)。同じノードのポートが近すぎる場合は、最小の間隔 (弧の長さ 14px) を空けて円周上に広げる (`domain/ports.ts` の `spreadAngles`)。
* TP を展開したノードは円を大きくする (半径 = max(11, ポート数 × 14 / 2π))。エンジンは、この半径を衝突・間隔に使う。
* **レイヤごとに別の領域**に配置する (レイヤ間のリンクは無い)。stress では、レイヤごとにレイアウトしてグリッドに並べる (間隔 120px)。force では、レイヤごとの領域の中心へ弱い力で引く。
* リンクは直線。同じノード間 (TP 間) の複数のリンクは、ポート間の別々の線として描く。
* エンジンは `LayoutEngine` ('force' | 'stress') で選ぶ。force 以外は `LayerLayoutFn` (レイヤのノードとリンクを受け取り、中心座標を返す非同期関数) として差し替えられる。
* 表示するレイヤが全部読み込まれてから配置する (レイヤごとに配置し直さない)。同じグラフ (ノード・半径・リンクが同じ) は配置し直さない。ノードを手で動かした場合は、他のノードは動かさない (stress)、または力学で緩やかに動く (force)。

### 3.2 stress (自前のストレス最小化) — 既定

`layout/stress.ts`。Gansner, Koren, North「Graph Drawing by Stress Majorization」(2004) の方法。

* **距離**: 画面上の 2 ノードの距離が、グラフ上の最短経路の長さに近くなるようにする。リンク 1 本の長さは `edgeGap (50) + 両端ノードの半径`。最短経路は Dijkstra (ヒープ)。重みは `1 / 距離²`。
* **反復**: 各ノードを 1 つずつ動かす局所版 (Gauss-Seidel)。最大 200 回。全ノードの移動量の合計がリンク長の 0.2% × ノード数を下回れば収束とみなす。
* **連結成分ごと**に別々に配置する。孤立ノードは 1 ノードの成分。成分はグリッドに並べる (間隔 60px)。
* **複数回の初期化**: 成分ごとにランダムな初期配置から最小 6 回、時間予算 (400ms) の内なら最大 max(最小回数の 3 倍, 12) 回まで試し、**リンクの交差数 × 100 + ノードの重なり × 10** が最小のものを採用する。0 になったら打ち切る。400 ノードを超える成分は 1 回のみ。
* **重なりの除去**: 収束後、近すぎるノード (半径の和 + 8px 未満) を反復して押し離す。
* 乱数は差し替えられる (テストで再現させるため)。

### 3.3 force (d3-force)

`forceRenderer.ts`。

* 力: リンク (距離 = 70 + 両端の半径、強さ 0.5)、斥力 (-(80 + 8 × 半径))、衝突 (半径 + 20、3 回)、レイヤ領域の中心へ (強さ 0.05)。
* **ウォームアップ**: 新しいグラフは、300 ティックを先に進めてから表示する (アニメーションしない)。
* **複数回の初期化**: stress と同じく、交差・重なりが最小のものを採用する (最小 6 回、時間予算 (500ms) の内なら最大 max(最小回数の 3 倍, 12) 回。交差・重なりが 0 になれば打ち切る)。力学法は、1 回の初期化だと「ねじれた」配置 (リンクが交差した状態) に落ち着くことが多い (4 ノードのリングで 58%)。
* ノードを動かすと、力学が動いて周囲が緩やかに動く。ノード・レイヤの追加は、既存ノードの位置を保ったまま行う。

### 3.4 品質の指標と比較の画面

* 指標: **リンクの交差数** (ノード間の直線の組で、端を共有しないものの交差)、**ノードの重なり** (円が重なる深さの合計)、**所要時間** (配置の開始から終了まで)。
* 画面: ツールバーの「Compare layouts」で 2 つのエンジンを左右に並べる。選択・ホバー・トレースは両方で共有される。URL に `?layout=<engine>&compare=<engine>` が入るので、共有・再現できる。

## 4. 検討した選択肢

| 案 | 内容 | 結論 |
|---|---|---|
| force (d3-force) + 改善 | ウォームアップ、複数回の初期化、ポート配置 | **採用** (もう 1 つのエンジンとして残す。コンパクトで、動かすと周囲が動く) |
| 自前のストレス最小化 | 標準的な手法を自前で実装 | **採用 (既定)**。ELK stress と同等以上の品質で、数倍速い。依存なし |
| ELK (elkjs) の layered / stress / force | Eclipse Layout Kernel。ポートと配線も扱える | **不採用**。stress は自前に及ばず、layered は密なメッシュで不向き、force は劣る。EPL-2.0 の対応と約 1.5MB が必要 (5、6 参照) |
| Graphviz (WASM) | dot (階層)・neato/sfdp | **不採用** (未実装)。約 1.5MB で、展開・折りたたみのような対話的な更新に不向き |
| WebCola / Cytoscape の cola・fcose | 制約付き force | **見送り**。現状の品質で足りる。必要になれば再検討 |
| ホップ数による階層化 (自前) | 基準ノードからの距離で段に分ける | **見送り**。階層表示は段階 4 の dependency 表示で扱う |
| 手動調整 + 保存 | 配置を手で直して保存 | **見送り**。保存先 (バックエンドの書き込み API) が必要。必要になれば再検討 |

## 5. 検証結果 (実データ)

条件: 実データのレイヤをノード単位で配置 (TP は円周上のポート)。ヘッドレス Chrome で、画面に表示される指標を読み取った。各セルは「所要時間 / リンクの交差数」。ノードの重なりは全エンジン・全データで 0。ELK の初回の読み込み時間は含まない。

| データ (ノード, リンク) | force (d3) | **stress (自前)** | ELK stress | ELK layered | ELK force |
|---|---|---|---|---|---|
| mddo-fw layer3 (54, 66) | 529 ms / 21 | **267 ms / 6** | 885 ms / 12 | 280 ms / 110 | 654 ms / 162 |
| mddo-mregnw layer1 (40, 55) | 526 ms / 11 | **128 ms / 5** | 453 ms / 10 | 128 ms / 5 | 320 ms / 46 |
| mddo-mregnw layer3 (85, 110) | 790 ms / 41 | **434 ms / 10** | 1326 ms / 15 | 225 ms / 285 | 1184 ms / 329 |
| mddo-mregnw layer2 (140, 85) | 1264 ms / 1 | **22 ms / 0** | 322 ms / 0 | 161 ms / 0 | 199 ms / 0 |
| mddo-bgp layer3 (53, 54) | 535 ms / 7 | **49 ms / 0** | 540 ms / 0 | 134 ms / 62 | 496 ms / 106 |
| mddo-fw 全 7 レイヤ (222, 213) | 2244 ms / 69 | **344 ms / 14** | 978 ms / 22 | 317 ms / 181 | 913 ms / 349 |
| mddo-mregnw 全 5 レイヤ (315, 300) | 3605 ms / 78 | **602 ms / 15** | 1818 ms / 25 | 469 ms / 305 | — |

所見:

* **stress (自前) は、全データで ELK stress と同等以上** (交差数は 7 データ中 5 で少なく、2 で同じ。所要時間は 2〜10 倍短い)。force (d3) よりも交差が少ない (全データで)。
* **ELK layered** は、疎な階層構造 (mregnw layer1・layer2) では交差が最小かゼロだが、L3 のような密なメッシュ (セグメントノードが多数の機器をつなぐ) では交差が大幅に増える (110・285)。上から下への流れが明確になる、という別の性質があり、交差数だけでは比べられない。
* **ELK force** は他に劣る。
* 配置は、stress が最もコンパクト (間隔の既定が ELK の既定 (140) より短いため)。
* 注意: ELK layered の交差数は、ELK が返す折れ点つきの経路で数えている (直線で数えると不当に悪くなる)。

## 6. ELK を採用しなかった理由とライセンスの分析 (記録)

**理由:** (a) 品質で自前の stress に及ばない (5)、(b) ライセンスへの対応が必要、(c) 約 1.5MB (gzip で約 450KB) のチャンクが要る (遅延読み込みで他には影響しないが、使うときに待たされる)、(d) 自前実装 (約 250 行 + テスト) で同等以上の結果が出た。

**ライセンスの分析** (技術的な整理であり、法的な判断ではない。ELK を再度検討する場合の出発点として残す):

* elkjs 0.12.1 は `EPL-2.0 OR GPL-3.0-or-later`。同梱の `LICENSE.md` は EPL-2.0 の全文。本プロジェクトは MIT。配布物の依存は ELK 以外はすべて MIT / ISC / BSD。
* EPL-2.0 は弱いコピーレフト。**Modified Works** (改変物) だけが対象で、ライブラリを `import` して使うだけのコードは含まれない (§1 の定義)。改変せずに使えば、netoviz2 本体は MIT のままにできるという読み方が自然。
* 配布 (コンテナイメージ、ブラウザへの配信を含む。「Distribute」は、コピーを入手できる状態にすることも含む) するときの要件:
  * §3.1(a): ソースコードの入手方法を明示する (elkjs と Eclipse ELK のソースは公開されている)。
  * §3.1(b): 別のライセンス (MIT) での配布は、免責があり、受領者の EPL 部分の権利を制限しなければ可。
  * **§3.3: 著作権・ライセンスの表示を削除しない。** 検証した時点の本番ビルドは、ELK のヘッダのコメント (`Copyright (c) … Kiel University …`) を圧縮で消していた。使う場合は、`THIRD_PARTY_NOTICES` (EPL-2.0 全文、著作権表示、ソースの入手先) の同梱が必要だった。
  * 改変する場合は、改変部分を EPL で公開する。
  * §4 (商用製品に含めるときの補償義務) は、研究・OSS の範囲では通常は関係しない。特許の条項 (特許ライセンスの付与、訴訟による終了) にも注意する。
* `OR GPL-3.0-or-later` なので EPL を選べる。GPL を選ぶと、結合物全体が GPL になる。
* **ELK を再度採用する場合のチェックリスト**: EPL を選ぶ / 改変しない / `THIRD_PARTY_NOTICES` の同梱 (dist とイメージ。netoviz2 本体は MIT `LICENSE` を持つ) / 組織の OSS ポリシー・法務の確認。

## 7. 既知の限界と今後

* **階層表示**: ELK layered のような階層配置は持たない。レイヤ間の依存を階層的に見せる用途は、段階 4 の dependency 表示 (レイヤ帯) で扱う。
* **メッシュ状・密なグラフ**: stress でも交差はゼロにならない (L3 の大きなグラフで 10〜15 程度)。さらに減らすには、交差の局所的な改善 (ノードの入れ替え) などが考えられる。
* **ポート単位のレイアウト**: 現状はノードの配置の後でポートの向きを決めるため、ポートの位置は配置の最適化に使っていない。
* **大きなグラフ**: stress の距離行列は O(n²)。400 ノードを超える成分は 1 回のみの初期化にしている。さらに大きなグラフでは、Web Worker 化や距離の近似 (ピボット) が必要になる。
* **手動調整の保存**: 配置を保存して再現する機能は無い (保存先のバックエンド API が要る)。
* 配置は乱数に依存する。同じデータでも、開き直すと配置が変わる (再現が必要なら、乱数の種を URL に載せるなどの対応が要る)。

## 8. 検証と再現

* 画面で比較する: `http://localhost:15000/netoviz2/<network>/<snapshot>?layers=<layer>&layout=force&compare=stress` (各パネルの指標を読む)。
* 単体テスト: `npm test` (`src/render/layout/*.test.ts`、`src/render/forceRenderer.test.ts`)。stress は、サイクル・グリッド・複数成分・大きなノード・再現性を検証している。
* ブラウザでの測定: ヘッドレス Chrome を DevTools Protocol で操作し、各パネルの指標 (`[data-testid=layout-stats]`) を読む。**`--virtual-time-budget` は使わない** (`requestAnimationFrame` が進まず、force のシミュレーションが数ティックしか動かない)。
